# Workspace Usability Parity Plan

Date: 2026-05-28

## North Star

Helix should feel like a Google Workspace-class Drive and editor suite. Users should not need to know Helix-native formats. They should understand files by normal extensions and normal product categories: documents, spreadsheets, presentations, PDFs, images, and media.

The MVP bar is not "the parser has a fallback." The MVP bar is that the primary user paths are obvious, testable, and do not dead-end into "coming soon" for files that Drive, Docs, Sheets, and Slides already display.

## How We Get There

We do not get to Workspace-class functionality by cloning every menu item first. We get there by making the system behave correctly at the object/workflow layer, then deepening the editors.

1. Treat Google Workspace behavior as the product spec whenever user expectations are unclear.
2. Build one compatibility matrix for detection, routing, app-list bucketing, conversion capability, previews, and export.
3. Preserve originals in Drive and ask before creating editable native copies.
4. Store provenance on every converted native object so users and support can answer "what file did this come from?"
5. Make Drive metadata authoritative for app lists, sharing, starred, trash, ownership, preview, and lifecycle.
6. Require real browser/integration proof for every main workflow: upload, open, copy/convert, edit, autosave, reload, version rollback, share, search, preview, trash, restore, delete.
7. Keep unsupported states honest: legacy `.doc`, `.ppt`, and other formats can be detected and previewed/downloaded before they are editable.
8. Only after the workflow is trustworthy, keep expanding editor depth: comments, suggestions, rich object drag/drop, formulas, slide objects, print/page settings, exports, and collaboration polish.

## Workspace Parity Execution Model

Every Workspace-like feature should move through the same ladder:

1. Discover the current Google Workspace behavior from official docs or live research when the expected behavior is unclear.
2. Capture the user-facing contract in this plan: file family, surface, open behavior, edit behavior, preview behavior, save behavior, and unsupported state.
3. Implement the smallest vertical slice that makes the visible product more real.
4. Add permanent unit/component/integration coverage for the slice.
5. Prove it in the running browser against the actual local backend.
6. Record the exact proof here, including route, object id when useful, tools called, persistence/reload result, and any remaining warnings.

The working priority is:

1. Drive object model: upload, classify, preview, share, star, trash, restore, delete.
2. Open/edit model: native files open directly; foreign editable files preserve originals and ask before copy/convert.
3. Persistence model: autosave, reload stability, version history, restore, and make-copy across Docs, Sheets, and Slides.
4. Editor depth: top-ribbon controls must mutate real document/sheet/deck state, not just decorate the chrome.
5. Collaboration model: sharing roles, comments, suggestions, presence, notifications, and link access.
6. Interop model: import/export fidelity, Office round-tripping where feasible, honest preview/download states where not.
7. Search/AI model: cross-file search, in-document find/replace, citations, summaries, and assistive creation only after core file workflows are reliable.

Workspace reference checkpoints verified on 2026-05-28:

- Google Drive stores arbitrary file types and previews common Office, PDF, image, audio/video, archive, code, and text files; previews can be scaled-down approximations of the full file. Source: https://support.google.com/drive/answer/37603
- Google Drive opens native Google Docs/Sheets/Slides in their app, while videos, Microsoft Office files, audio, and photos open in Drive preview. Source: https://support.google.com/drive/answer/2423485
- Google Docs Editors can edit Office files directly, save Office-format changes, or convert Office files by making a copy when native-only features are needed. Source: https://support.google.com/docs/answer/9406611
- Docs, Sheets, Slides, and Vids expose version history with view, restore, and make-copy actions. Source: https://support.google.com/docs/answer/190843
- Drive supports list and grid layouts with thumbnails that help users understand files before opening them. Source: https://support.google.com/drive/answer/2375177

## Product Contract

1. Drive is the source of truth for every object.
2. Docs, Sheets, and Slides are filtered working views over Drive, not separate worlds.
3. Native Helix objects open directly into their editor.
4. Foreign editable formats open through an explicit copy/convert decision.
5. The original uploaded file is never mutated by conversion.
6. Converted copies appear in Drive and in the relevant app list.
7. Previewable files open in a real preview surface before download.
8. Unsupported files explain exactly what can happen next: download, keep in Drive, or retry after support lands.
9. User display preferences, such as card/list view, persist across Drive and app list surfaces.
10. Browser refresh and deep links keep the user on the current object.

## Copy/Convert UX

Clicking an importable foreign file should show a decision, not silently create a new native object:

- Title: "Create editable copy?"
- Body: explain that Helix will create an editable Docs/Sheets/Slides copy and keep the original unchanged in Drive.
- Primary action: "Create copy"
- Secondary action: "Preview only"
- Tertiary action: "Cancel"
- Download remains available from the details panel.

When the user creates a copy, the new native object should store source metadata:

- `importedFromDriveObjectId`
- `importedFromFilename`
- `importedFromFormat`
- `importedFromFormatLabel`
- `importedFromMimeType`
- `importedFromByteSize`
- `importedAt`

The converted copy should use a human title without the extension, but all file-list surfaces must continue showing real extensions for raw foreign files.

## Gotcha Catchers

1. Maintain one central detection table for routing, list classification, and conversion eligibility.
2. Add golden tests for every extension in the format matrix.
3. Add app-list tests proving `.ppt`, `.pptx`, `.xls`, `.xlsx`, `.doc`, and `.docx` appear in the expected app buckets.
4. Add Drive tests proving importable files show the conversion prompt and do not silently import.
5. Add details-panel tests proving "Open" uses the same conversion decision.
6. Add browser tests for card/list view persistence across Drive, Docs, Sheets, and Slides.
7. Add a no-primary-`Coming soon` assertion for Drive, Docs, Sheets, Slides, preview, and open routes.
8. Add visual checks that extensions remain visible when names truncate.
9. Keep legacy binary formats honest: if `.ppt`, `.xls`, or `.doc` are detected but not editable yet, show "Preview/download only" or "conversion not available" instead of a false editor open.
10. Seed the demo corpus with at least one file per supported family so regressions are visible in the UI.

## MVP Build Order

1. Stabilize Drive and app-list classification so users see files where they expect them.
2. Add explicit copy/convert prompt for importable foreign files.
3. Replace placeholder thumbnails with real preview-backed thumbnails for images, PDFs, sheets, slides, and docs.
4. Finish native editor persistence: autosave, version history, rollback, refresh-safe routing.
5. Bring editor controls into tight top ribbons across Docs, Sheets, and Slides.
6. Add real drag/drop behavior inside editors for images and common elements.
7. Expand conversion support and clearly label unavailable legacy formats.
8. Run integration/browser coverage against seeded Drive data before every demo.
