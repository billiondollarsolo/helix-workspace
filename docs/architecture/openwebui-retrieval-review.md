# Open WebUI retrieval and web search review

Helix can add admin-managed pgvector/Qdrant retrieval and web search by extending its existing configuration, search, and Assistant tools. The smallest useful implementation has two independent controls: **Workspace retrieval** and **Web search**. A vector database does not supply embeddings, and native web search does not require a vector database.

## Delivered scope

The implementation following this review adds saved Admin controls, safe connection tests, runtime status, and durable reindex jobs for Helix-managed pgvector or Qdrant retrieval. Settings activate after the configuration transaction commits; rejected settings preserve the saved configuration. Embedding provider, model, and dimensions are independent of Assistant memory's existing 768-dimensional storage.

Workspace retrieval now indexes overlapping passages across each supported source, rather than only its beginning. The existing `embeddingProvider.config.maxInputChars` selects chunk size (default 1,024; range 64–32,768); `chunkOverlapChars` selects overlap (default 15%; smaller than chunk size). Full-source classification precedes embedding. Up to 2,048 passages per source are supported; excess work fails visibly instead of silently dropping the tail. Embeddings are requested in batches of at most 32. The best matching passage represents each source in hybrid results, with its original source link. This bounds repetition; it is not exhaustive retrieval of every passage of a document.

Scan-clean UTF-8 text/code Drive files up to 512 KiB are read from storage, checked against their scanned SHA-256, and reloaded for current lifecycle and permissions. Other formats retain searchable metadata; PDF/Office extraction, OCR, viewers, and editors are not included. Current source text is hashed and matched again before a retrieved passage reaches the model. Source changes/deletions remove all of its old passages in both adapters. Backend, endpoint, model, dimensions, chunk size, overlap, and chunk-format changes select a new collection generation and require reindexing. Old generations are retained. Runtime blocked/chunked counters describe current-process indexing operations, not a durable file inventory.

Web-enabled turns offer native `web.search` for Brave or SearXNG and `web.fetch` to read public HTML/plain-text pages. They share the existing per-turn opt-in, current actor/policy checks, untrusted-source treatment, and exact source links. Public fetching never inherits the private-host exception for a configured SearXNG or vector endpoint. Native page reads do not need embeddings or put web content into the workspace vector index. This follows Open WebUI's native search/fetch path; its legacy automatic web-fetch/embed pipeline is a separate design.

See the [local retrieval runbook](../runbooks/local-ai-retrieval.md) for configuration, supported content, and live verification. The pre-feature comparison below records the starting point. External knowledge connectors and reranking remain separate from the delivered native fetch and document-chunking features.

This review pins Open WebUI source to [commit `0a7c15832fb30b1903753e83f81dc7d27e5b0944`](https://github.com/open-webui/open-webui/commit/0a7c15832fb30b1903753e83f81dc7d27e5b0944), the public `main` revision inspected on 10 September 2026, committed 4 September. Official documentation was inspected separately; where it differs, the pinned implementation takes precedence. This is source research, not a claim that Open WebUI was deployed or its tests were run.

## Native tool use follow-up

The September 2026 follow-up adopts Open WebUI's native function-call loop, not its custom Python tool/plugin execution runtime. The model receives structured schemas, chooses calls, sees correlated results or errors, and continues until it answers, needs approval, or reaches a configured limit. Tool output remains untrusted input. [Upstream tool assembly](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/tools.py#L522-L685), [execution loop](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/middleware.py#L5642-L5740).

| -------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool selection       | Native schemas filtered by configuration, capabilities, permissions, and chat features. | Authorized tool groups in the composer; web search remains a separate opt-in. Administration and Webhooks are off by default. Selection intersects current ACLs and slash-command scope. More than 128 selected tools produces an actionable error. |
| Iterations           | Default 256; environment override supports unlimited. Exhaustion reports an error.      | Default 128 execution rounds, configurable from 1–256 in Admin → AI providers. At the limit, request a final answer with native tool choice disabled.                                                                                               |
| Errors and ordering  | Correlated tool errors return to the model. Ordinary tool batches run sequentially.     | Sequential execution, classification carried forward between calls, cancellation checks, and recoverable malformed-argument errors without invoking the bad call.                                                                                   |
| Approvals            | Tool confirmation is part of its tool execution system.                                 | Existing server approval policy remains authoritative. Approval or cancellation resumes the same native loop with the original chat tool settings. Every subsequent write receives its own policy decision.                                         |

Open WebUI's current limit comes from [`CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS`](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/env.py#L1060-L1077); older descriptions of a ten-round default do not describe this revision. Its history utilities preserve matched native calls/results, and its source projection supplies citation metadata. [Native history conversion](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/misc.py#L325-L509), [source projection](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/middleware.py#L390-L493).

Search being enabled does not force a model to fetch every result, and a citation is not a factual accuracy check. For a weather question, the answer still needs a source for the requested location and date. Helix supplies the current date/time zone and tells the model to identify unverified details; it does not invent a forecast or guarantee correctness from a snippet. Existing fetch limits, public-host restrictions, tenant authorization, DLP, and per-action approval remain in force.

The local Admin API saved and read back 128 rounds, rejected 257, and denied a member's attempt to change the limit while preserving provider and web-search settings. Live GPT-OSS20B completed search and page reading, recovered from two HTTP 404 results, and retained its answer, exact source URLs, and tool activity on reopen. Live GPT-OSS120B completed the original weather prompt with two searches and three page-fetch attempts, recovering from an oversized page. A shared classification correction prevents calendar day numbers from being mistaken for payment cards and ordinary place restrictions from being mistaken for document sensitivity markings; actual cards, credentials, PII, and document classifications remain checked. Verification artifacts are stored outside Git in `helix-release-backups/2026-09-10/local-delivery-evidence/openwebui-tool-use`, with browser evidence in the adjacent `tool-ux` directory.

## What Open WebUI actually implements

### Configuration and activation

Current source stores configuration as individual SQL `config` rows, with JSON values and update timestamps. Reads query the database; writes are awaited upserts that surface failures. Environment values supply defaults. `ENABLE_PERSISTENT_CONFIG=false` instead keeps updates in process defaults, which do not survive restart. The current implementation has replaced the older single-JSON-row/PersistentConfig machinery still described in some material. [Configuration model](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/models/config.py#L101-L222), [environment reference](https://docs.openwebui.com/reference/env-configuration/#enable_persistent_config).

This does **not** mean every setting changes live. `VECTOR_DB`, `PGVECTOR_DB_URL`, and Qdrant connection settings are read from the environment. The vector factory instantiates a module-level client. Changing the internal vector backend therefore requires a process restart and an explicit indexing/migration plan. The Documents admin page changes embedding and retrieval settings; it is not a live internal-vector-backend switch. [Startup configuration](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/config.py#L501-L670), [vector factory](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/vector/factory.py).

### Internal vector storage

Both pgvector and Qdrant implement a common collection/insert/search/query/delete interface. The pgvector implementation creates a chunk table and vector/text indexes, validates the stored vector dimension, and refuses an automatic change of an existing index method. Its application database and vector connection can share PostgreSQL infrastructure. [pgvector adapter](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/vector/dbs/pgvector.py#L61-L288).

Qdrant's “multitenancy” mode consolidates logical collections into a few physical collections. It maps file, memory, web-search, and knowledge collection names to a payload `tenant_id`, adding that filter to operations. That identifier represents the logical Open WebUI collection; it is not a replacement for Helix's organization identity and actor permissions. Changing collection naming or mode requires migration care. [Qdrant mapping and filters](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/vector/dbs/qdrant_multitenancy.py#L100-L300).

### Files, embeddings, and retrieval

The ingestion route extracts content, splits it into chunks, records the embedding engine/model in chunk metadata, embeds the chunks, then writes text, metadata, and vectors. Files have their own `file-{id}` collection; adding them to knowledge also targets a knowledge collection. The route verifies file ownership or administrative authority and requires write access for a supplied destination collection. [Ingestion and file processing](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/routers/retrieval.py#L1637-L1903).

Retrieval supports vector search and hybrid lexical/vector retrieval, with optional reranking and relevance limits. The Documents page provides embedding engine/model, chunking, and reindex controls, and explicitly tells administrators to reindex after changing the embedding model. A query vector must come from a compatible model and dimension; choosing a chat model alone does not configure this. [Retrieval utilities](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/utils.py#L415-L614), [Documents UI](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/src/lib/components/admin/Settings/Documents.svelte#L980-L1190).

Native `query_chat_files` restricts input to attached, currently readable files before retrieving chunks. Files are not treated as permanently authorized merely because an earlier conversation attached them. Updating/deleting a file propagates cleanup to associated knowledge embeddings. [Chat-file retrieval](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/tools/builtin.py#L2498-L2600), [file lifecycle](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/routers/files.py#L721-L758).

### External knowledge is a separate feature

Open WebUI also has an experimental Admin integration for querying an **already populated** pgvector, Qdrant, or Milvus database. It stores a connection, source collection/table mapping, and knowledge access grants. The combined source-create route executes a sample retrieval and rejects an empty result before saving; update has a corresponding test flow. This is distinct from selecting the database in which Open WebUI indexes its own uploads. [Official RAG guide](https://docs.openwebui.com/features/chat-conversations/rag/#external-knowledge-sources-external-vector-databases), [source creation](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/routers/knowledge.py#L926-L1036), [admin UI](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/src/lib/components/admin/Settings/ExternalKnowledge.svelte).

External Qdrant retrieval queries the configured collection; external pgvector uses quoted, validated identifiers and parameterized values. Neither path automatically imports arbitrary upstream document ACLs into Open WebUI's knowledge grants. Therefore a Helix equivalent would need an explicit trusted-source authorization model, not just a database URL. This broader connector feature is unnecessary for enabling Helix-managed semantic indexing. [External retrieval implementation](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/external.py#L95-L280).

### Native web search

The native tool catalog adds `search_web` and `fetch_url` only when the global setting, model capability, built-in category, chat/default feature, and user permission all allow them. The model then chooses when to search or fetch. This is more than a settings-page switch: the policy must control tool availability and execution. [Tool injection](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/tools.py#L677-L685), [official agentic-search guide](https://docs.openwebui.com/features/chat-conversations/web-search/agentic-search/).

`search_web` returns titles, links, and snippets, capped by the administrator's result count. `fetch_url` extracts page text. Neither native operation performs chunking, embedding, or vector storage. Current source limits fetched text only when `web.fetch.max_content_length` is configured. The agentic guide's statement about a hardcoded 50,000-character limit is stale relative to this revision. [Native web tools](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/tools/builtin.py#L293-L367).

Legacy web search instead generates queries, fetches result pages, and optionally stores/retrieves their chunks; native mode deliberately skips that automatic path. The middleware converts native results into citation sources for the chat UI. Helix should implement the native path first, without introducing ephemeral web-vector collections. [Legacy/native branching](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/middleware.py#L2669-L2678), [citation projection](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/middleware.py#L420-L498).

The admin Web Search UI selects a provider and credentials and configures result counts, fetch behavior, and confirmation. A small Helix first version can support Brave's fixed HTTPS API and SearXNG's configured JSON endpoint. Open WebUI normalizes both into the same result shape; Brave uses `X-Subscription-Token`, while SearXNG needs `format=json`. Self-hosting SearXNG still sends queries to its configured upstream engines. [Web Search UI](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/src/lib/components/admin/Settings/WebSearch.svelte#L160-L210), [Brave adapter](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/web/brave.py), [SearXNG adapter](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/web/searxng.py).

## Security properties to preserve

Open WebUI validates fetched URL schemes, parser-confusing characters, host filters, and resolved IPv4/IPv6 addresses. Its connection adapters repeat address checks at the actual connection, closing the DNS-rebinding gap. Redirect and browser-subresource paths also need validation. Its source explicitly warns that a proxy may resolve the target instead, bypassing connection-layer destination checking. These are reasons to reuse a tested outbound transport rather than use raw `fetch` after a one-time URL check. [URL and connection defenses](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/retrieval/web/utils.py#L81-L293).

Helix must distinguish a trusted administrator-configured private Qdrant/SearXNG endpoint from an arbitrary URL chosen by a model or returned by a search engine. Public page fetching should reject private destinations even during local development. Do not apply the database endpoint allowance to page fetches. Do not forward browser cookies, provider credentials, or tenant headers to result sites.

Open WebUI's instance admin is root-equivalent in its documented single-tenant architecture. Helix has organizational boundaries, delegated administration, actor ACLs, DLP, and data classification. Copying the admin UI is reasonable; copying that trust model is not. [Open WebUI administrative trust model](https://docs.openwebui.com/reference/env-configuration/#appbackend).

Search queries and embedding requests are outbound data transfers. Helix must apply classification/DLP before either network call, preserve untrusted source treatment and citations afterward, and avoid logging raw private queries or credentials. A local LLM does not make an external search or embedding service local.

## Proposed configuration and runtime contract

Use the existing configuration mechanism. The table describes the design considered during research; the delivered implementation retains existing persisted field names and now includes native page fetching and document chunk retrieval, as described above.

| Configuration       | Required fields and behavior                                                                                                                                                                                                                                                                                     |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace retrieval | Disabled / pgvector / Qdrant. Pgvector uses Helix's configured PostgreSQL, without requesting a second database password. Qdrant takes an endpoint and write-only key. Display configured versus active revision and a safe health/test result.                                                                  |
| Embeddings          | Explicit provider endpoint, write-only key, model identifier, and verified dimension. Store an embedding fingerprint with the index generation. A changed model or dimension requires a new index generation; never query old vectors with a new model silently.                                                 |
| Retrieval limits    | Bounded top-K and bounded context size. Start with existing hybrid ranking and existing indexing policy; chunk size and overlap are operator settings; an additional reranker is not included.                                                                                                                   |
| Web search          | Disabled by default; provider enum Brave / SearXNG, provider-specific key or endpoint, finite result count, request timeout, concurrency and page-size limits. A failed search is an actionable error, not a fabricated answer or an unannounced provider fallback.                                              |
| Assistant use       | A typed per-chat web-search flag, gated by current admin policy and actor scope. Revalidate at execution as well as tool listing. Native `web.search` returns structured title/URL/snippet/source IDs; `web.fetch` returns extracted text, canonical/final URL, content length and explicit truncation metadata. |
| Secret updates      | Omitted secret preserves the stored value; explicit clear has a deliberate representation. GET returns only `apiKeyConfigured`. Connection tests neither persist drafts nor expose credentials.                                                                                                                  |

For a managed internal index, pgvector is the simplest default because Helix already operates PostgreSQL and RLS. Qdrant is useful where operators want a separate vector service, but it adds another backup, connection, credentials and lifecycle boundary. Both should share the same authorization contract. A separate “query my existing arbitrary external knowledge database” integration can follow if requested; it should not be hidden inside this switch.

## Implementation sequence

1. Add strict settings/readback and connection tests, including embedding dimensions, redaction and finite limits. Render independent retrieval and web-search forms using the existing admin patterns.
2. Repair and test the existing vector adapters and canonical result authorization. Reuse the durable index/reindex path; make activation status honest and preserve a working generation until replacement succeeds.
3. Register native search/fetch tools only for authorized, opted-in turns. Reuse the outbound transport with public-destination restrictions, classification/DLP, cancellation and structured citation output.
4. Prove the complete path with isolated PostgreSQL/pgvector and authenticated Qdrant, a controlled search provider/server, and one configured live search. Keep the user's local database and existing files intact.

## Acceptance tests

- Admin save/readback survives restart; member and cross-organization configuration attempts fail; concurrent edits preserve unrelated settings.
- Keys never appear in GET, audit payloads, logs, validation errors, browser bundles or provider errors. Omitted keys survive edits; explicit deletion works.
- Enabling pgvector with valid embeddings produces real indexed results; disabled retrieval makes no embedding/vector call. Keyword-only operation remains available.
- Qdrant tests use actual authentication, two organizations, private/shared resources, valid point IDs and repeated collection creation. Test create/upsert/query/delete rather than mocking only HTTP shapes.
- Two actors in one organization cannot retrieve one another's private Mail, Chat, or Drive data. Grant, revoke, trash, quarantine, and delete changes apply before a hit reaches the model, even with a stale index.
- A changed embedding model with the same dimension still triggers generation compatibility rules. A dimension mismatch fails clearly. Failed/cancelled reindex leaves the current generation intact and reports progress/error honestly.
- Web tools are absent or denied when disabled, not opted in, or unauthorized, including direct forged tool invocations and a mid-conversation policy change.
- Search requests honor provider authentication, count caps, Retry-After and bounded retries. Empty results, 401, 429, 5xx, invalid JSON and cancellation are visible and recoverable.
- Public fetch rejects loopback, RFC1918, link-local/metadata targets, IPv6 variants, userinfo/parser-confusing URLs, redirect-to-private and DNS rebinding. Trusted local provider endpoints do not exempt returned result URLs.
- Page responses have bounded bytes/time, supported content types, safe text extraction, explicit truncation, and no credential forwarding across redirects. Search snippets and fetched pages remain untrusted instructions.
- Restricted input cannot be exported through an embedding request, search query, URL query string or subsequent model turn. Public external results receive server-owned provenance/classification without lowering existing conversation restrictions.
- Browser flow proves admin enable/test/save, Assistant opt-in, a real native search plus follow-up fetch, clickable citations, cancellation and reopen persistence. Accessibility covers labels, focus, keyboard operation and status/error announcements.
